1 · La méthode en une image — trois étages

Le fichier fait 183 lignes, mais il ne contient que trois choses : une suite de gardes (les conditions), une collection de petites fabriques (une par message), et un seul point de sortie. Il ne lit aucune base de données, n'appelle aucun réseau : tout lui est donné en argument — sauf trois valeurs qu'il va chercher lui-même, et c'est déjà le premier point intéressant.

3 · Les 7 gardes — ce qui est annoncé, ce qui est testé

Voici le corps réel de la méthode. C'est une cascade if / else if : le premier vrai gagne et court-circuite les six autres.

Trois de ces prédicats portent un nom qui promet plus que ce qu'ils font. Les voici dépliés : 

// La signature annonce deux parametres… le corps n en utilise qu un
private boolean showNotCompatibleContextualMessage(Boolean isDeviceBrandCompatible, Mode mode) {
    return !isDeviceBrandCompatible;                       // mode IGNORE
}

private boolean showLowBatteryContextualMessage(Mode mode) {
    return deviceInfo.isBatteryLow() && !deviceInfo.isBatteryChargeSustained();   // mode IGNORE
}

private boolean showPowerSavingContextualMessage(boolean isRecording, Mode mode) {
    return deviceInfo.isPowerSavingModeEnabled() && !isRecording;               // mode IGNORE
}

private boolean showPolicyEffectiveContextualMessage(CMTProfile profile) {
    return profile != null
        && profile.getPolicyEffectiveDate() != null
        && profile.getRemainingDaysUntilPolicyTakesEffect() > 0;     // strictement > 0
}

C'est une interface, pas une classe. Elle hérite de ContextualMessage, qui définit cinq champs — et rien d'autre. Aucune notion de « quel cas s'applique » : le message qui sort ne sait pas pourquoi il existe.

#Le piègeCe que ça change pour la migration
1 Le texte est traduit dans la fabrique. localizedStringSource.get(...) est appelé 19 fois ici, au moment où la décision est prise. C'est le point structurant. Tant que la traduction a lieu ici, le Kotlin reçoit une phrase finie et ne peut rien en faire. En Kotlin, le domaine émettra quel cas s'applique et la traduction descendra dans la présentation.
2 Le cas n'est jamais transporté. L'objet de sortie a cinq champs, dont aucun ne dit « je suis le message batterie faible ». Impossible de trier une liste, de dédupliquer, ou d'émettre un événement analytics par type. Le sealed à 8 variantes règle ce point par construction.
3 mode est un paramètre mort dans les règles 1, 3 et 4 : il est passé, la signature l'annonce, le corps l'ignore. Ne pas recopier le vestige. En Kotlin, mode n'entre que dans la règle 5 — trois signatures allégées.
4 Batterie faible et économie d'énergie partagent l'icône CONTEXTUAL_MESSAGE_BATTERY. Seule la teinte les distingue, et la teinte n'est jamais lue en aval. Deux variantes distinctes (LowBattery, PowerSaving) et la teinte devient une propriété du cas, dérivée dans la présentation. Devient bloquant avec la liste de trois.
5 Trois messages sur sept sortent sans teinte (marque, appareil, badge) — et le badge sort même sans icône. L'écran « devine » aujourd'hui. En Kotlin, chaque variante déclare explicitement son icône et sa teinte : plus de devinette, et les previews couvrent les 8 cas.
6 Le type concret trahit le polymorphisme. ExecutableContextualMessageImpl implémente ExecutableContextualMessage et AjustoContextualMessage, mais pas BadgeContextualMessage — donc il tombe dans le else du bridger et son buttonExecutable() est perdu. Le when exhaustif d'un sealed rend cette classe d'erreur impossible : le compilateur refuse un cas oublié.
7 Le bouton est mort sur toute la chaîne. La lambda capture une WeakReference vers un listener que setListener() ne remplit jamais — aucun appelant. Et dans TripServiceImpl, les deux instanceof échouent donc toujours. Ce n'est pas une régression à éviter : la fonctionnalité n'existe pas. Décision D2 — on modélise buttonText dans le domaine, on ne rend pas le bouton tant que le produit n'a pas défini la modale.
8 Le badge est un cas à part. title() = le nom du badge venu du serveur ; message() = une clé i18n variable selon le niveau ; et si le niveau sort de 1-6, getBadgeLevelText() rend null, donc get(null). La variante Kotlin transporte les trois informations (badgeIdentifier, badgeTitle, badgeLevelKey) et la présentation décide du libellé. Décision D4 à trancher : nom du badge ou félicitations ?
Deux détails mineurs, mais qui disent quelque chose sur l'état du fichier.
① topClaimableBadgeFinder.getBadge() est appelé avant la cascade, donc le calcul du meilleur badge est fait à chaque battement, même quand la règle 1 gagne immédiatement. Sans conséquence fonctionnelle, mais c'est du travail jeté.
② Deux méthodes statiques — showingForLessThan20Days() et shouldTrackScoreVariation() — n'ont aucun appelant dans les deux dépôts. Ce sont les vestiges d'une fonctionnalité « variation de score » (voir l'icône SCORE_VARIATION, jamais produite non plus). À ne pas porter.

Choisir l'icônePrésentation — le mapper Une icône est une décision d'affichage, pas une décision métier.
Choisir la teintePrésentation — le mapper Devient une propriété du cas : les jumelles batterie/éco cessent d'être confondues.
Traduire le textePrésentation — AjustoLocalizedString Traduire au moment de l'affichage, plus au moment de la décision. Le changement de langue devient explicite au lieu de fonctionner par accident.
Porter la lambda du boutonPrésentation — une Action MVI Plus de WeakReference, plus de instanceof : une action typée que le compilateur vérifie.
Transporter l'objet BadgeDomaine — trois champs plats Aucun type Core ne traverse la frontière ; le claim se fait par identifiant.
Le résumé en une phrase. findContextualMessage() fait aujourd'hui trois métiers dans une seule méthode : elle décide, elle habille, et elle traduit. La migration ne change pas ce qu'elle décide — l'invariant de parité le prouve à chaque build — elle sépare seulement les trois métiers. Et c'est cette séparation, à elle seule, qui fait disparaître cinq des huit pièges ci-dessus sans avoir à les corriger un par un.
