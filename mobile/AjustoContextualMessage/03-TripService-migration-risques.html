Bonne nouvelle stratégique. Le bridger a une surface d'attaque minimale : un flux en lecture, aucun appel de commande, aucun état partagé avec TripService. Il ne participe pas au cycle de vie du service — c'est le AjustoDashboardFragment qui appelle tripService.cancel() dans onDestroy, pas lui.

Conséquence : tu n'as pas besoin de migrer TripService. Tu as besoin de remplacer une seule de ses 24 sorties. Ce n'est pas la même ambition.
Mais deux absences comptent.
  • setListener(Listener) n'est jamais appelé par le bridger. Or c'est par là que remonte le clic du bouton « marque non compatible » : buttonExecutable → listener.onModalClick() → TripServiceImpl.executableListener → downcast sur AjustoSnapListener → onDeviceNotCompatibleModalClick(). Sans setListener, le bouton reste muet même si on porte l'exécutable.
  • cancel() n'est jamais appelé non plus. Le bridger annule son propre SCRATCHSubscriptionManager, pas le service. C'est correct — mais ça veut dire que le service reste vivant tant que le Fragment legacy existe.

Le bridger entrant, en code réel

/*
 * Matching ios implementation: iosapp/app/legacy/bridger/ajusto/AjustoRepositoryBridger
 *     - CmtRepository: Kore      ← le NOUVEAU, en KMP
 *     - AjustoRepository: Core   ← l'ANCIEN contrat Java
 */
object CmtRepositoryBridger : AjustoRepository {        // ← interface CORE JAVA

    private lateinit var repository: CmtRepository       // ← implémentation KMP
    private val repositoryScope = CoroutineScope(Dispatchers.IO + SupervisorJob())

    fun injectCmtRepository(cmtRepository: CmtRepository) { repository = cmtRepository }

    override fun createAjustoLoginOperation(): SCRATCHOperation<CMTProfile?> =
        object : SCRATCHOperationCoroutine<CMTProfile?>(coroutineScope = repositoryScope) {
            override suspend fun suspendedRun() {
                val koreOutput = repository.createCmtLoginOperation()      // ← appel KMP
                when (val result = KoreTranslator.handleKoreResponse(koreOutput)) {
                    is Success -> dispatchSuccess((result.data as CmtProfile).asCore)
                    is Error   -> dispatchOperationResultWithError(SCRATCHUnknownError())
                }
            }
        }
}

L'outil qui rend ça possible — un adaptateur coroutine → SCRATCHOperation :

abstract class SCRATCHOperationCoroutine<A>(coroutineScope: CoroutineScope) : SCRATCHBaseOperation<A>() {
    private val operationScope = coroutineScope.plus(SupervisorJob())
    override fun cancel()      { super.cancel(); operationScope.cancel() }
    final override fun internalRun() { operationScope.launch { suspendedRun() } }
    abstract suspend fun suspendedRun()
}
Pourquoi c'est décisif. Le bridger sortant permet d'exposer le Core au KMP — c'est ce que fait AjustoContextualMessageBridger. Le bridger entrant permet de remplacer un morceau du Core par du KMP sans que le Core s'en aperçoive.

C'est le seul vecteur réaliste de migration de TripService : on ne remplace pas TripServiceImpl, on remplace ses dépendances, une par une, en laissant un bridger entrant pour que le Java continue de fonctionner. Le Core devient progressivement une coquille qui orchestre du KMP.

Le raccourci qu'on oublie

Si l'objectif est uniquement le message contextuel, il existe un chemin plus court que les 10 vagues : porter la cascade (vague 8) en KMP, et alimenter ses 7 entrées par des bridgers sortants individuels plutôt que par une migration.

7 · Les 9 risques

IMPACT CRITIQUEPROBA HAUTE

R1 · Casser iOS via J2ObjC

TripService.java porte @ObjectiveCName sur 10 de ses 24 méthodes. L'interface est transpilée en Objective-C et consommée par l'app iOS. Toute modification de signature — même un renommage — casse la compilation iOS.

Mitigation : ne jamais modifier TripService. Ajouter à côté, ne pas transformer. Le bridger entrant préserve la signature exacte.

IMPACT HAUTPROBA HAUTE

R2 · Dépôt séparé, cycles de release décalés

ad-digital-mobile-core-lib et ad-digital-mobile-aio sont deux dépôts. Le Core est consommé comme artefact Artifactory. Une modification du Core suppose : PR sur l'autre dépôt, release, montée de version chez toi, régression sur tous les consommateurs.

Mitigation : le bridger entrant vit dans ton dépôt (androidApp/bridger/). Tu changes l'implémentation sans toucher au Core — c'est exactement ce que fait déjà AccountRepositoryBridger.

IMPACT CRITIQUEPROBA MOYENNE

R3 · Le SDK télématique n'est pas portable

CMTTripManager, CMTTripProvider, CMTSessionController, CMTSettingsController, CMTEvent, CMTGeolocation, CMTTrip — 7 types du wrapper Cambridge Mobile Telematics. C'est du natif par nature (permissions, capteurs, service en arrière-plan).

Mitigation : accepter qu'ils resteront derrière un expect/actual ou un bridger, définitivement. Ne pas les mettre dans le périmètre.

IMPACT HAUTPROBA HAUTE

R4 · SCRATCH ≠ Flow — les sémantiques ne se superposent pas

Quatre comportements SCRATCH n'ont pas d'équivalent direct :

SCRATCHComportementÉquivalent Flow
notifyEventIfChanged(v)déduplique à l'émissiondistinctUntilChanged() — mais côté consommateur
clearLastResult()vide le cache : les nouveaux abonnés ne reçoivent rienaucun — un StateFlow garde toujours sa valeur
subscribeOnce()un seul événement puis désabonnementfirst() — mais sémantique de complétion différente
SCRATCHObservable.Tokenhandle d'annulation réassignableJob — mais pas réassignable en place

Le piège concret : clearLastResult(). Le Core l'appelle à la déconnexion (isAuthenticated == false). Un StateFlow KMP conservera la dernière valeur — c'est exactement la vulnérabilité V9 identifiée sur le Summary. Toute migration doit modéliser ce reset explicitement.

IMPACT HAUTPROBA MOYENNE

R5 · État mutable partagé dans TripServiceImpl

8 champs mutables + 12 SCRATCHObservableImpl avec cache interne, sans synchronisation explicite hormis un AtomicBoolean. contextualMessageToken est réassigné à chaque événement du combineLatest — donc l'ancien token est perdu sans être annulé.

Mitigation : ne pas réécrire ce fichier. Le contourner par les dépendances.

IMPACT MOYENPROBA HAUTE

R6 · Ordre d'initialisation du constructeur

Le constructeur appelle registerObservables() puis 6 méthodes notifyXxx() dans un ordre précis. Ces méthodes créent des abonnements croisés entre observables. Un portage qui change l'ordre — ou qui rend une dépendance lazy — produit un état initial différent, souvent visible seulement au premier lancement après installation.

Mitigation : tests d'intégration sur le premier lancement, pas seulement sur les relances.

IMPACT MOYENPROBA MOYENNE

R7 · Le downcast du listener

public void onModalClick() {
    if (listener instanceof TripService.AjustoSnapInProgressListener) {
        ((AjustoSnapInProgressListener) listener).onLimitedFeedbackModalClick();
    } else if (listener instanceof TripService.AjustoSnapListener) {
        ((AjustoSnapListener) listener).onDeviceNotCompatibleModalClick();
    }
}

Un instanceof en cascade sur une interface marqueur vide (interface Listener { }). Le comportement du bouton « marque non compatible » dépend du type dynamique de ce qui a été passé à setListener(). Aucun contrat ne dit lequel.

Mitigation : identifier qui appelle setListener() aujourd'hui avant de brancher ce bouton sur le Summary. Si personne ne l'appelle depuis le nouvel écran, le bouton restera muet quoi qu'on fasse côté bridger.

IMPACT HAUTPROBA MOYENNE

R8 · Régression silencieuse de la cascade

La cascade est un if / else if à priorité stricte. Une réimplémentation qui inverse deux branches ne plante pas : elle affiche simplement le mauvais message dans les cas où deux conditions sont vraies simultanément — par exemple batterie faible et badge réclamable. Ce sont les cas les plus rares, donc les moins testés.

Mitigation : une table de vérité exhaustive en commonTest — 7 conditions booléennes, tester les combinaisons où plusieurs sont vraies, pas seulement une à la fois.

IMPACT MOYENPROBA HAUTE

R9 · Double source de vérité pendant la transition

Tant que AjustoDashboardFragment et AjustoSummaryFragment cohabitent — et ils cohabitent : les deux implémentent AjustoTabViewPagerFragment, donc sont instanciés ensemble dans le ViewPager — il y a deux abonnements au même observable, produisant deux rendus. Si la cascade est dupliquée en KMP (voir le raccourci §6), ça devient deux calculs distincts.

Mitigation : décider explicitement qui est la source de vérité, et borner dans le temps la période de cohabitation.

Que prend AjustoContextualMessageBridger de TripService ? Une propriété sur 24 : getContextualMessageObservable(), plus deux opérateurs SCRATCH (observeOn, subscribe) et trois types Core (AjustoContextualMessage, BadgeContextualMessage, ExecutableContextualMessage.Icon). Il n'appelle ni cancel() ni setListener(). Surface : 4,2 %.
Que faut-il migrer d'abord ? Pas des méthodes de TripService — des dépendances de la cascade. Dans l'ordre : DeviceInfo (★☆☆☆☆), puis LocalizedStringSource/BrandLogic, Badge+BadgeScoper+TopClaimableBadgeFinder, AjustoDeviceCompatible. Les quatre sont indépendantes entre elles. La cascade elle-même vient en 8ᵉ, et c'est la plus facile.
Quelles autres dépendances ? 44 imports non-JDK en 5 familles : 7 du SDK télématique CMT (non portables), 18 du framework SCRATCH (paradigme entier), 2 du DI Itch, 1 d'i18n Circumflex, 26 du domaine DGAG. Plus ClassifyInviteChecker, BadgeScoper, TopClaimableBadgeFinder instanciés dynamiquement dans notifyContextualMessage() — invisibles dans le constructeur.
Le verdict, en une phrase. TripService n'est pas à migrer : il est à évider. On ne touche ni à son interface (iOS en dépend) ni à son implémentation (775 lignes, 18 dépendances, un SDK natif). On remplace ses dépendances une par une par du KMP, derrière des bridgers entrants — un patron déjà en production dans ce projet avec AccountRepositoryBridger et CmtRepositoryBridger. Le message contextuel, lui, n'a pas besoin d'attendre : il sort par un bridger sortant qui ne coûte que 4,2 % de la surface du service.
