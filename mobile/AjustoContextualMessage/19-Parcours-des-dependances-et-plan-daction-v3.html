Le doc 17 décrit le chemin actuel — six flux assemblés dans le Core, une cascade qui rend du texte déjà traduit, cinq couches traversées. Ça n'a pas changé. Ce qui change ici, c'est la chaîne cible, et surtout l'endroit où chaque décision est prise.

Le principe, en une phrase : le domaine répond à « quelle règle s'applique », la présentation répond à « qu'est-ce qu'on livre ce trimestre ». Ce sont deux questions de nature différente — l'une stable et portée par le code Java qu'on migre, l'autre volatile et décidée par le produit. Les coder au même endroit ferait qu'un changement de portée rouvre le code métier.

Concrètement, quatre signaux sur huit sortent aujourd'hui à l'écran — GoodToKnow, LowBattery, PowerSaving, Badge. Les quatre autres sont résolus, mappés et testés, mais filtrés avant l'affichage. Les activer, plus tard, c'est déplacer une ligne d'un bloc à l'autre dans ContextualMessageActivation : le domaine les résolvait déjà, le mapper les traduisait déjà, la vue les affichait déjà.

Pourquoi ça compte pour le lot 7. Le critère de sortie de la migration est l'invariant resolve(signals).filterNot { it is GoodToKnow }.firstOrNull() == cascadeJava(signals). Si le domaine n'évaluait que 4 règles sur 8, cette égalité deviendrait invérifiable — on perdrait le seul moyen mécanique de prouver qu'on n'a rien cassé. C'est la raison technique, pas seulement stylistique, pour laquelle le filtre est en présentation.

3.3 · Les previews qui se vérifient toutes seules V3

La convention de l'écran est déjà posée : les jeux de données vivent dans des classes …MockProvider du paquet preview/, les fonctions de preview sont centralisées dans AjustoSummaryScreen.kt, et elles utilisent @DgagPreview et @TpicPreview plutôt que @Preview nu. Mes previews actuelles de AjustoSummaryMessageBox font le contraire des trois — à aligner.

Mais on peut aller plus loin que « ne pas oublier d'ajouter une preview ». L'idée est de dériver les previews de la hiérarchie scellée, avec deux garde-fous complémentaires.

Garde-fou 1 — le compilateur

Un when exhaustif sans else dans le catalogue. Le jour où quelqu'un ajoute un 9e type au sealed, le fichier cesse de compiler : impossible de l'ignorer, il faut venir y ajouter son exemplaire.

C'est exactement le même mécanisme que ContextualMessageActivation — deux fichiers, un seul principe.

Garde-fou 2 — la CI

Le when force à ouvrir le fichier ; il ne force pas à remplir la liste. Un test compare le catalogue à AjustoContextualMessage::class.sealedSubclasses et échoue si un type n'a pas d'exemplaire.

Les deux ensemble donnent la garantie : état déclaré ⇒ preview générée.

Le PreviewParameterProvider dérive du catalogue, et Compose génère une preview par valeur de la séquence. Trois familles de valeurs : la liste vide — l'état normal à ne pas régresser —, chaque type un par un, et enfin l'empilement réel filtré par ContextualMessageActivation, qui documente visuellement ce que la production affiche aujourd'hui.

Bénéfice secondaire : les previews passent par le vrai ContextualMessageMapper. Si une clé de traduction ou une teinte change, la preview le montre, au lieu de mentir avec des chaînes écrites à la main — ce que font mes previews actuelles. Et le catalogue devient le jeu d'exemples commun aux tests du use case et à ceux du mapper.

Les limites, dites franchement. Compose nomme les previews par index, pas par type : le panneau affichera « … 1, 2, 3 » — les titres des MessageBox les rendent malgré tout identifiables. sealedSubclasses ne rend que les sous-classes directes : suffisant ici, la hiérarchie est plate, mais la garantie tomberait si on imbriquait des sous-sealed. Enfin, un exemplaire par type ne couvre pas les variantes d'un même type — badge or contre argent, 1 jour contre 30 : le catalogue peut en porter plusieurs, mais la garantie porte sur « au moins un par type ».

  1. Un grep sur ca.dgag.ajusto.core dans le chemin du message — du repository jusqu'au composable — ne remonte rien.
