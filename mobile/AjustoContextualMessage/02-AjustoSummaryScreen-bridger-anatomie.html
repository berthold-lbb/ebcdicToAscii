1 · La chaîne complète : 6 couches, 1 seule source

Différence structurelle majeure avec le Dashboard : là où le Dashboard avait deux sources écrivant dans un même StateFlow (ViewModel KMP + SCRATCH direct), le Summary n'en a qu'une. Tout passe par le ViewModel KMP. Le message contextuel arrive par une branche latérale — le shim — au lieu d'un abonnement dans le Fragment.

Le AjustoSummaryShimImpl en détail

class AjustoSummaryShimImpl(
    private val deviceInfo: DeviceInfo,                              // Kore
    private val networkState: NetworkState,                          // Kore
    private val contextualMessageSource: AjustoContextualMessageSource,  // KMP ← le bridger
    dispatcher: CoroutineDispatcher = Dispatchers.Default
) : AjustoSummaryShim {

    private val shimScope = CoroutineScope(SupervisorJob() + dispatcher)   // jamais annulé

    override val state: StateFlow<AjustoSummaryShimState> = combine(
        deviceInfo.isLocationEnabledStateFlow,                        // flow 1
        networkState.connectionTypeStateFlow,                         // flow 2 — valeur IGNORÉE (_)
        contextualMessageSource.contextualMessagesStateFlow       // flow 3 — NOM FAUX (voir V1)
    ) { isLocationEnabled, _, contextualMessage ->
        AjustoSummaryShimState(
            hasNetworkAccess  = networkState.hasNetworkAccess(),      // appel impératif
            isLocationEnabled = isLocationEnabled,
            isBatteryLow      = deviceInfo.isBatteryLow(),            // appel impératif
            contextualMessage = contextualMessage
        )
    }
    .onStart      { contextualMessageSource.startObserving() }        // ← branche le legacy
    .onCompletion { contextualMessageSource.stopObserving()  }        // ← débranche
    .stateIn(shimScope, SharingStarted.WhileSubscribed(5_000), currentState())
}
Le placement de onStart/onCompletion est correct. Ils sont appliqués avant stateIn, donc sur le flow amont — ce qui les rend bien pilotés par le WhileSubscribed(5_000). L'intention est juste : le legacy n'est abonné que tant qu'un écran KMP regarde. C'est la section suivante qui explique pourquoi ça ne fonctionne pas en pratique.

4 · Le cycle de vie start/stop — neutralisé

Figure 4 — Le init{} du bridger court-circuite le pilotage du shim

sequenceDiagram autonumber participant KI as KoreInitializer participant BR as Bridger (object) participant AS as AndroidScope participant KO as Koin participant SH as AjustoSummaryShimImpl participant VM as AjustoSummaryViewModel Note over KI: demarrage de l application KI->>BR: val src = AjustoContextualMessageBridger activate BR Note over BR: premier acces -> bloc init execute BR->>BR: startObserving() BR->>BR: started = false donc on continue BR->>BR: started = true BR->>AS: AndroidScope.get()[TripService::class.java] Note over AS: si le scope n est pas encore peuple : CRASH AS-->>BR: tripService BR->>BR: subscribe(autoSubscriptionManager) deactivate BR Note over BR: ABONNE, hors de tout cycle de vie KI->>KO: AndroidKoin.start(startupInputs) KO->>KO: single AjustoContextualMessageSource = bridger Note over VM: l ecran s ouvre plus tard VM->>SH: collecte de shim.state SH->>BR: onStart -> startObserving() BR->>BR: if (started) return Note over BR: NO-OP — deja demarre depuis le boot Note over VM: l ecran se ferme, 5s passent SH->>BR: onCompletion -> stopObserving() BR->>BR: started = false, subscriptionManager.cancel() Note over BR: MAINTENANT seulement le pilotage devient reel
Trois conséquences.
  • Risque au démarrage — AndroidScope.get()[TripService] est appelé avant AndroidKoin.start(). Si le scope Itch n'est pas encore peuplé, c'est un crash au lancement.
  • Le premier onStart est un no-op — la garde if (started) return le neutralise. Le WhileSubscribed(5_000) ne contrôle rien tant qu'un stopObserving() n'a pas eu lieu.
  • Le cycle de vie a deux propriétaires — le bloc init avant le premier stop, le shim après. Le comportement diffère selon le moment.
Pourquoi l'argument « capturer le message avant que le ViewModel existe » ne tient pas. Un StateFlow conserve sa dernière valeur par construction, et un SCRATCHObservable republie son état courant à la souscription (notifyEventIfChanged côté Core garde le dernier résultat, sauf après clearLastResult()). Supprimer le bloc init ne perd donc rien, et rend le schéma onStart/onCompletion conforme à ce qu'il prétend faire.

6 · Les 11 vulnérabilités

BLOQUANT

V1 · contextualMessagesStateFlow vs contextualMessageStateFlow

Le ShimImpl lit une propriété avec un S qui n'existe pas. La source expose contextualMessageStateFlow, sans S. Deux occurrences : dans le combine(...) et dans currentState().

// AjustoSummaryShimImpl.kt
contextualMessageSource.contextualMessagesStateFlow     // ← n'existe pas
// AjustoContextualMessageSource.kt
val contextualMessageStateFlow: StateFlow<…>       // ← la vraie

Effet : le module ne compile pas. C'est le seul écart purement mécanique qui reste.

HAUTE

V2 · messageIconTint() n'est jamais lu → batterie ≡ économie d'énergie

Le Core produit deux messages avec la même icône BATTERY et des teintes différentes : RED pour batterie faible, WARNING pour économie d'énergie. Le bridger teste uniquement l'icône.

isLowBatteryMessage = messageIcon() == CONTEXTUAL_MESSAGE_BATTERY   // vrai dans les DEUX cas

Effet : impossible de distinguer les deux situations en aval. Détaillé en §7.

HAUTE

V3 · Aucun composable MessageBox dans le Summary

grep -c 'MessageBox' AjustoSummaryScreen.kt → 0. SummaryContent rend Header, ScoreGauge, TripGauge, InformationalList. Le champ uiState.messageBox est calculé et jamais lu.

Effet : quelle que soit la qualité de la chaîne en amont, rien n'apparaît à l'écran.

HAUTE

V4 · payload.iconKey rempli puis ignoré → 4 icônes sur 7 perdues

Le bridger fait correctement iconKey = messageIcon().toContextualIconKey(). Le toMessageBox() du ViewModel ne le lit pas et retombe sur QuestionMark pour tout ce qui n'est ni badge ni batterie.

Effet : marque non compatible, appareil non compatible, classifier et police en vigueur affichent tous un point d'interrogation.

MOYENNE

V5 · buttonExecutable jeté → bouton « marque non compatible » mort

Le message règle 1 est un ExecutableContextualMessage qui porte un buttonExecutable() — un callback vers listener.onModalClick(), lui-même relayé par TripServiceImpl.executableListener vers l'écran via un downcast sur TripService.Listener. Le bridger le range dans la branche else et ne récupère que le libellé.

Effet : le bouton s'afficherait sans rien faire. Et même en le portant, il faudrait qu'un setListener() ait été appelé — ce que le Fragment legacy fait et pas le Summary.

MOYENNE

V6 · Textes du badge non substitués

Le Core renvoie title = claimableBadge.getTitle() (le nom du badge, ex. « Freinage doux niveau 3 ») et message = badgeLevelText. Le Fragment legacy les remplace par AJUSTO_DASHBOARD_NEW_MEDAL_TITLE et CONTEXTUAL_MESSAGE_CLAIM_BADGE_BUTTON — c'est-à-dire « Félicitations pour votre nouvelle médaille! / Touchez pour la réclamer ». Le bridger prend les valeurs brutes.

Effet : le Summary afficherait le nom du badge à la place du message produit. Régression visible par l'utilisateur, invisible en revue de code puisque les deux textes vivent dans des fichiers éloignés.

MOYENNE

V7 · NavigateToClaimedBadgeView tombe dans else -> {}

Le ViewModel émet bien l'événement sur OnClaimBadge. Le when d'ObserveAsEvents dans AjustoSummaryRoot gère Dismiss, NavigateToAchievementsView, NavigateToDrivingView, NavigateToTripsView, NavigateToHistoryView, NavigateToScoreView — puis else -> {}.

Effet : même si la carte badge était rendue et cliquable, le clic ne mènerait nulle part. Note : Success, Failure et DisplayLocationPermissionDialog tombent aussi dans le else.

MOYENNE

V8 · badgeIdentifier transporté mais jamais utilisé

Le bridger le remplit (badge().identifier), le payload le porte, et personne ne le lit. Le toMessageBox() émet AjustoSummaryAction.OnClaimBadge — une action sans paramètre. L'information de quel badge réclamer se perd entre le payload et l'action.

Effet : quand la navigation sera branchée, il faudra re-résoudre le badge, probablement via AjustoBadgeControllerBridger.findBadge(identifier) — donc il faudra bien récupérer l'identifiant depuis uiState.contextualMessage, pas depuis l'action.

MOYENNE

V9 · Le StateFlow survit à la déconnexion

Côté Core, registerObservables() appelle contextualMessageObservable.clearLastResult() quand isAuthenticated passe à false. Ça vide le cache Core. Le MutableStateFlow du bridger, lui, conserve sa dernière valeur.

Effet : après une déconnexion puis reconnexion avec un autre compte, le message du compte précédent reste dans le StateFlow jusqu'à ce que le Core en recalcule un nouveau. Fuite d'information entre sessions.

FAIBLE

V10 · isBatteryLow et hasNetworkAccess lus impérativement

Dans le combine du shim, seuls trois flows déclenchent une réémission. deviceInfo.isBatteryLow() et networkState.hasNetworkAccess() sont des appels de fonction évalués au moment où l'un des trois flows émet. Et la valeur du flow réseau est même ignorée (_).

Effet : si la batterie devient faible sans qu'aucun des trois flows n'émette, isBatteryLow reste périmé. En pratique le Core observe getIsBatteryLowObservable() et publiera un message contextuel — donc c'est indirectement rattrapé. Fragile mais pas cassé.

FAIBLE

V11 · shimScope jamais annulé

CoroutineScope(SupervisorJob() + Dispatchers.Default) créé dans le constructeur, sans cancel() nulle part. Le shim étant un singleton Koin, il vit toute la durée du processus.

Effet : acceptable pour un singleton, mais rend le shim intestable en isolation (impossible de le fermer entre deux tests). Un scope injecté serait préférable.

La même situation, dans les trois architectures

Dashboard legacy

getKoreIconKeyFromImageKey(BATTERY, WARNING) → BatteryLow(WARNING) → icône dgag_icn_low_battery teintée dgag_battery_power_saving_color.

Visuel : ✅ correct — orange, distinct du rouge.

Analytics : ⚠️ faux positif — if (messageIcon() == BATTERY) déclenche lowBatteryContent() pour l'économie d'énergie aussi.

Summary actuel

isLowBatteryMessage = true (indistinguable), puis BatteryLow(WARNING) codé en dur dans le ViewModel.

Visuel : ❌ rien — pas de composable.

Sémantique : ❌ perdue — le domaine ne sait pas qu'il s'agit d'économie d'énergie. Ironie : la couleur WARNING tombe juste ici, mais elle est fausse pour « batterie faible » qui devrait être rouge.

Analytics : ❌ absente.

Cible feature-structured

icon == BATTERY && tint == RED → LowBattery ; sinon → PowerSaving. Deux types distincts dans le domaine.

Visuel : ✅ — l'icône et la couleur se déduisent du type, plus besoin de les transporter.

Analytics : ✅ — deux événements distincts, plus de faux positif.

Ce que le faux positif signifie pour tes données. L'événement lowBatteryContent mélange deux populations : les utilisateurs dont la batterie est réellement critique (risque de perte de collecte de trajets) et ceux qui ont simplement activé le mode éco, batterie éventuellement à 80 %. Le mode éco étant bien plus fréquent, l'erreur va toujours dans le même sens : surestimation du problème batterie. Toute décision produit basée sur cette métrique part d'un chiffre gonflé.
