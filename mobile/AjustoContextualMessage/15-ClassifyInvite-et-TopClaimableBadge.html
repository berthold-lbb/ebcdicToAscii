Les deux algorithmes de la cascade

ClassifyInviteChecker (règle 5) et le duo BadgeScoper → TopClaimableBadgeFinder (règle 7) : ce qu'ils calculent exactement, avec des exemples chiffrés.

0 · Où ils se branchent

Sur les sept règles de la cascade, cinq sont de simples comparaisons de booléens. Deux seulement font un vrai calcul, et elles ne sont pas construites de la même façon : ces deux-là sont des objets jetables, fabriqués à neuf à chaque battement du flux, puis passés à la cascade.

La meilleure nouvelle du dossier est là. Ces trois classes sont des calculateurs sans état : elles reçoivent tout par le constructeur, elles ne touchent ni au réseau, ni au SDK, ni à la plateforme. 1 · ClassifyInviteChecker — « invite-le à étiqueter ses trajets »

1.1 · Le besoin métier, tel qu'il est écrit dans le code

/*
 Je suis un nouvel utilisateur :
 qui a complete les 5 premiers trajets
 qui n a labele aucun trajet
 Je vois le bandeau informatif qui me suggere de labeler mes trajets.
 Je le vois tant que je n ai pas labele de trajet jusqu a mon 20e trajet. Apres le bandeau disparait.
 Le processus se repete pour un resnap.
*/

Traduit en une phrase : « montre le bandeau aux nouveaux, entre le 6ᵉ et le 20ᵉ trajet, tant qu'ils n'ont rien étiqueté ». Le code met cinq conditions pour dire ça — et la dernière phrase du commentaire (« le processus se répète pour un resnap ») n'est pas implémentée, on y revient.

L'asymétrie à connaître. Le plancher (« plus de 5 ») accepte l'un ou l'autre des deux compteurs, mais le plafond (« au plus 20 ») ne regarde que numberOfTrips, celui du serveur.
Conséquence : si le compteur serveur est en retard ou à zéro alors que la base locale contient 50 trajets, la condition ② passe par la voie locale, la condition ③ passe parce que 0 <= 20 — et le bandeau reste affiché bien au-delà du 20ᵉ trajet. Ce n'est pas théorique : les deux sources se désynchronisent naturellement (le serveur compte la vie du compte, le local ne garde que 90 jours).

La condition ④ est une fenêtre glissante : elle ne voit que les trajets encore présents dans la liste filtrée. La condition ⑤ est une mémoire permanente : une fois le drapeau posé, il n'est jamais retiré, puisque qualify() n'a aucun appelant.

La conséquence, et c'est la phrase du commentaire qui ne tient pas. « Le processus se répète pour un resnap » — non : rien ne remet le drapeau à zéro. Un utilisateur qui étiquette un trajet une seule fois, puis recommence un nouveau contrat (resnap), ne reverra jamais l'invitation. Soit l'appelant manquant est dans un fichier hors dépôt, soit la fonctionnalité n'a jamais été branchée. À trancher avant de porter : reproduire le comportement réel, ou implémenter l'intention du commentaire ?

2 · BadgeScoper → TopClaimableBadgeFinder — « quelle médaille proposer ? »

La règle 7 se joue en deux temps, dans deux classes. La première range, la seconde choisit. Il faut comprendre ce qu'est un badge avant d'entrer dans le rangement.

  1. Le badge ne connaît ni sa famille ni son niveau : il les déduit de son identifiant, par deux expressions régulières. "SNAP3" → famille SNAP, niveau 3.
  2. « Réclamable » = débloqué mais pas encore encaissé : completedDate != null && claimedDate == null. Un badge déjà réclamé n'est plus réclamable.
  3. Il y a six niveaux nommés : Novice, Apprenti, Expert, Maître, As, Légende. Le nombre 6 n'est pas une constante déclarée : c'est la taille de cette liste.

Le badge « TURN » ne peut jamais produire de message. La famille est déclarée dans Badge.java (8 constantes) mais la table de rangement n'en enregistre que 7. Un badge dont l'identifiant commence par TURN n'entre dans aucune échelle, donc reste invisible pour le sélecteur — même s'il est réclamable.
C'est la décision D1 : on reproduit ce comportement à l'identique, on le documente, et on le verrouille par un test nommé turn_badges_sont_ignores() qui deviendra rouge le jour où le produit tranchera. Reste la question au backend : l'API renvoie-t-elle réellement des badges TURN ?

2.3 · Temps 2 — TopClaimableBadgeFinder choisit

Il parcourt les sept échelles dans l'ordre, et dans chaque échelle il monte les barreaux du plus bas au plus haut. Il s'arrête au premier badge réclamable dont le suivant ne l'est pas — ou qui est le dernier de l'échelle. 

for (List<Badge> badgeScope : scopedBadgeList) {          // SNAP d abord, ACCEL en dernier
    for (Badge badge : badgeScope) {                       // du niveau le plus bas au plus haut
        int i = badgeScope.indexOf(badge);
        if (badge.isClaimable()
            && (i == badgeScope.size() - 1                  // il est le dernier barreau
                || !badgeScope.get(i + 1).isClaimable()))   // ou le barreau du dessus ne l est pas
        { claimableBadge = badge; break; }
    }
    if (claimableBadge != null) break;                     // une seule echelle gagne
}

Dit en français : « le plus haut palier débloqué d'affilée, dans la famille la plus prioritaire ». Trois exemples valent mieux qu'une définition.

La priorité entre familles est un ordre figé dans le code, pas une règle métier écrite quelque part. Si un badge SNAP et un badge ACCEL sont réclamables en même temps, c'est toujours le SNAP qui est proposé — parce que SNAP est à l'index 0 de la table. À porter à l'identique, et à documenter, car rien dans le code ne dit que c'est intentionnel.

2.4 · Les quatre défauts de ce duo

#Le défautEffet, et ce qu'on en fait
1 Le rangement modifie les badges qu'il reçoit. La deuxième passe appelle setPreviousBadge() et setNextBadge() sur les objets Badge venus du BadgeProvider — donc sur des objets partagés avec le reste de l'application. Calculer le message contextuel a un effet de bord sur l'état des badges. En Kotlin, AjustoBadge est une data class : le chaînage devient une construction de copies. Résultat identique, effet de bord disparu.
2 indexOf(badge) compare par valeur. La boucle demande l'index d'un badge qu'elle est en train de parcourir, via equals() — qui compare une douzaine de champs. Sur deux badges identiques dans la même échelle, l'index renvoyé est celui du premier : le test « le barreau du dessus » regarde alors le mauvais voisin. En Kotlin on utilise l'index de boucle — correct sur des données saines et sur des données douteuses.
3 Le niveau 0 est accepté par le rangement. Le filtre est level >= 0, mais getBadgeLevelText() ne connaît que les niveaux 1 à 6 et rend null en dehors. Un badge de niveau 0 réclamable produirait un message dont le texte est get(null). À border explicitement dans le port Kotlin.
4 Le chaînage clone. setNextBadge() stocke un clone du voisin, qui lui-même a un voisin cloné… Travail et mémoire dépensés à chaque battement du flux, pour une information dont la règle 7 n'a pas besoin. En Kotlin, on ne reconstruit le chaînage que là où il sert réellement — la réclamation en cascade.

3 · Ce que ça donne en Kotlin

Les deux algorithmes sont du calcul pur : ils se portent sans pont, sans adapter, sans dépendance. C'est le lot 1 du plan — celui qui peut démarrer aujourd'hui, sans rien attendre. 

// REGLE 5 — ~10 lignes, aucune dependance
class ClassifyInviteRule {
    operator fun invoke(s: AjustoContextualSignals): Boolean =
        s.mode == AjustoMode.CONTINUOUS_V4 &&
        (s.numberOfTrips > MIN_TRIPS || s.recentTripCount > MIN_TRIPS) &&
        s.numberOfTrips <= MAX_TRIPS &&
        !s.hasUserLabeledRecentTrips &&
        !s.hasEverLabeledATrip          // ex-CLASSIFY_INVITE_DISMISSED, renomme

    companion object { const val MIN_TRIPS = 5; const val MAX_TRIPS = 20 }
}

// REGLE 7 — le rangement, sans mutation
class BadgeScopeResolver {
    operator fun invoke(badges: List<AjustoBadge>): List<List<AjustoBadge>> =
        AjustoBadgeScope.entries.map { scope ->
            badges.filter { AjustoBadgeScope.from(it.groupIdentifier) == scope }
                  .filter { it.level in 0..SUPPORTED_BADGE_LEVELS }
                  .sortedBy { it.level }
        }
    companion object { const val SUPPORTED_BADGE_LEVELS = 6 }
}

// REGLE 7 — la selection, avec l index de boucle
class TopClaimableBadgeSelector {
    operator fun invoke(scoped: List<List<AjustoBadge>>): AjustoBadge? {
        scoped.forEach { scope ->
            scope.forEachIndexed { i, badge ->
                if (badge.isClaimable && (i == scope.lastIndex || !scope[i + 1].isClaimable))
                    return badge
            }
        }
        return null
    }
}
