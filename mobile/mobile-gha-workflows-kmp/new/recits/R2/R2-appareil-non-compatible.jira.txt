h2. Contexte

Le message prévient la personne que son téléphone ne peut pas mesurer ses trajets correctement.
Il repose sur deux vérifications combinées : le serveur dit si ce modèle est sur liste blanche, et
l'appareil dit s'il possède les quatre capteurs nécessaires.

Ce récit porte aussi un sujet qui dépasse le message lui-même : *le stockage typé*. Le Core écrit
sa valeur de cache en entier natif, alors que l'interface de stockage du KMP ne connaît que les
chaînes de caractères. Lire cette clé avec l'accesseur de chaîne lève une exception de conversion
— pas une valeur nulle. Il faut donc étendre le stockage avant de pouvoir lire le cache, et
c'est ce récit qui le fait. Le récit de l'invitation à étiqueter s'appuiera dessus.

h2. Objectif

Brancher le signal de compatibilité de l'appareil, activer la règle 2, afficher le message, et
livrer au passage les accesseurs typés du stockage.

h2. Périmètre

h2. Le signal et la règle

Le signal ④ vaut vrai quand *les deux* conditions sont réunies : le modèle est sur liste blanche
côté serveur, et l'appareil possède ses quatre capteurs — position, réseau cellulaire, gyroscope,
accéléromètre.

La règle 2 se déclenche quand le signal est faux. Elle porte le nom du programme d'assurance, qui
s'interpole dans le texte affiché — d'où le signal ⑬.

Dans la cascade de la famille appareil, elle s'insère *entre* la règle de la marque et celle de la
batterie. Si R1 est déjà livré, il n'y a qu'une branche à ajouter au bon endroit ; l'ordre est
porté par les priorités et se vérifie par un test.

h2. Points de vigilance

{panel:title=(!) Le repli sur le cache est inversé dans le code d'origine|borderStyle=solid|borderColor=#2c5282|titleBGColor=#e6edf5|bgColor=#ffffff}
Le Java lit sa valeur de cache avec une valeur par défaut de moins un, puis n'agit *que si la
valeur lue est égale à cette valeur par défaut* — c'est-à-dire seulement quand le cache est
absent. Et dans ce cas il publie « incompatible », puisque moins un n'est pas un.

Autrement dit : quand le cache contient une vraie réponse, elle est ignorée ; quand il est vide,
on publie le pire résultat possible. Les deux branches sont à l'envers.

*Le comportement attendu ici est celui qu'on aurait écrit dès le départ* : on interroge le
serveur ; en cas de succès on publie la réponse et on met le cache à jour ; en cas d'échec on
publie la valeur en cache si elle existe, et à défaut on considère l'appareil compatible — parce
qu'afficher à tort « votre téléphone ne fonctionne pas » est bien plus coûteux que de ne rien
afficher.

C'est une correction délibérée d'un défaut d'origine. Elle doit être écrite en commentaire et
verrouillée par un test, sinon elle sera reprise à l'identique par un futur relecteur qui
comparera au Java.
{panel}

{panel:title=(!) Deux autres points|borderStyle=solid|borderColor=#c1c7d0|titleBGColor=#f4f5f7|bgColor=#ffffff}
*La clé de cache ne doit pas changer de nom ni de type.* Elle est écrite en entier natif par le
Core, dans la même instance de préférences chiffrées que le stockage KMP. Changer l'un ou l'autre
ferait repartir de zéro toutes les installations existantes — et surtout, tant que le Dashboard
hérité coexiste, les deux implémentations doivent lire la même valeur.

*Le rafraîchissement au retour en avant-plan fait partie du comportement.* Le Core relance l'appel
à chaque passage au premier plan. Ne pas l'oublier : sans lui, une réponse serveur ancienne peut
rester affichée indéfiniment.
{panel}

h2. Critères d'acceptation

h3. CA-1 — Le stockage typé lit ce que le Core a écrit

*Étant donné* une valeur entière écrite sous la clé de compatibilité par le code hérité
*Quand* on la lit avec le nouvel accesseur entier
*Alors* on obtient la même valeur, sans conversion ni exception

h3. CA-2 — Le signal combine bien les deux vérifications

*Étant donné* les quatre combinaisons de « sur liste blanche » et « capteurs présents »
*Quand* on évalue le signal
*Alors* il n'est vrai que lorsque les deux le sont

h3. CA-3 — Le repli fonctionne dans le bon sens

*Étant donné* successivement : le serveur répond « compatible », le serveur répond
« incompatible », le serveur échoue avec un cache existant, le serveur échoue sans cache
*Quand* on interroge la source
*Alors* elle rend respectivement compatible, incompatible, la valeur en cache, puis compatible par
défaut

h3. CA-4 — Le cache est mis à jour après une réponse réussie

*Étant donné* une réponse serveur
*Quand* elle est reçue
*Alors* la valeur est écrite sous la même clé, dans le même type, et une relecture la retrouve

h3. CA-5 — La règle 2 s'insère au bon rang

*Étant donné* une marque incompatible *et* un appareil non compatible
*Quand* on appelle le use case
*Alors* il rend le message de la marque, et lui seul

*Et étant donné* un appareil non compatible *et* une batterie faible
*Alors* il rend le message de l'appareil, et lui seul

h3. CA-6 — Le message porte le nom du programme

*Étant donné* le message rendu
*Quand* on le traduit en présentation
*Alors* le nom du programme d'assurance apparaît à la place prévue dans le texte

h3. CA-7 — Le message s'affiche réellement

*Étant donné* l'activation mise à jour
*Quand* on ouvre l'écran avec un appareil non compatible
*Alors* la boîte apparaît avec son libellé, son icône et sa teinte, et sa preview affiche le rendu
définitif

h3. CA-8 — Le rafraîchissement au retour en avant-plan

*Étant donné* l'application ramenée au premier plan
*Quand* l'écran se réaffiche
*Alors* une nouvelle interrogation du serveur a eu lieu

h3. CA-9 — Compilation et couverture

*Étant donné* la campagne de tests
*Quand* on l'exécute
*Alors* les modules compilent et le code livré ici est couvert à 100 %
